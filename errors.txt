CONCLUSIONS FROM THE PLY PROBE

1. PLYLoader parses the mesh successfully in Node.
2. position.count is 66034.
3. geometry.index.count is 129345, exactly 43115 triangles x 3 indices.
4. Every index is within [0, 66033]. The observed maximum is 66031.
5. geometry.drawRange is the full default range.
6. boundingBox and boundingSphere are finite.
7. Vertex colors are normalized Uint8Array RGB data, which Three.js materials can consume as vertex colors.
8. The geometry requires 32-bit element indices because it references more than 65535 vertices. This is the main Mesh-only WebGL compatibility risk. If the browser context is WebGL1 without OES_element_index_uint, the indexed mesh can fail to render even though Open3D and PLYLoader accept it. A WebGL2 context supports this index type.
9. The mesh and point-cloud bounds are nearly the same, so the mesh data itself is not obviously outside the camera.
10. No manual triangulation or index creation is required.

LIKELY ROOT CAUSE TO VERIFY IN THE BROWSER

The strongest Mesh-only failure candidate is the 32-bit indexed geometry:

- geometry.index.array is Uint32Array because the mesh has 66034 vertices.
- Three.js can render this in WebGL2.
- WebGL1 needs the OES_element_index_uint extension.
- If the current Canvas context is WebGL1 and the extension is absent, the mesh draw can fail or produce a WebGL error while point clouds and line/point modes continue to render because they do not require indexed triangle elements.

This is more specific and testable than blaming the PLY file, vertex colors, normals, camera framing, or drawRange.

SOURCE LIFECYCLE RISKS, LIMITED TO MESH RENDERING

1. MeshModel is kept mounted even when visible is false. Scene always renders <MeshModel visible={mode === "mesh"} />. This allows MeshModel state and a prior loaded geometry to survive mode changes.

2. The loader effect depends on geometry:

[visible, geometry, onSceneTransform]

The effect sets geometry itself, so geometry does not belong in the request effect dependency list. requestedRef currently prevents most duplicate loads, but this is unnecessarily coupled.

3. The PLYLoader request is not invalidated on unmount. A late success callback can call onSceneTransform and setGeometry after the user has switched away.

4. MeshModel and PointCloud both call the same onSceneTransform callback. PointCloud is also mounted while hidden and can asynchronously overwrite the shared parent transform after MeshModel computes its transform.

5. The shared Scene transform is stored at lines 768-791 and applied to the common group at lines 833-844. There is no Mesh-specific transform state.

6. Because the point-cloud and mesh bounds are close, the transform race is not proven to be the reason for total mesh invisibility, but it is a real Mesh rendering risk and can produce stale framing.

MINIMAL FIX DIRECTION FOR THE NEXT DEVELOPER

Do not refactor PointCloud, ConfidenceMap, CameraTrajectory, or the whole Scene.

First verify the WebGL2/Uint32 index condition. If the context lacks 32-bit element-index support, the smallest Mesh-only fix should address only MeshModel geometry compatibility or the Canvas context, while preserving the existing PLY URL and working modes. Avoid toNonIndexed() unless memory impact is measured, because it expands a 66k-vertex indexed mesh and may recreate the browser crash.

Independently make MeshModel's loader callback cancellation-safe and prevent late MeshModel callbacks from mutating the shared transform after Mesh has been hidden. This is a MeshModel-only lifecycle correction.

Do not change PointCloud or ConfidenceMap drawRange behavior.
